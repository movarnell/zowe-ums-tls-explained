Correct separation: UMS remains encrypted

AT-TLS handles eligible Zowe sockets. The App Server opens a separate HTTPS session to the UMS API server. UMS is excluded from the incompatible Zowe rule set, so its native TLS layer receives the handshake it expects. Excluding UMS from AT-TLS does not mean using HTTP to UMS.

02 / Where the conflict starts

A matching prefix is not a safe boundary.

Documented requirement

Watch the UMS job name

Zowe prefix       ZWE1
UMS suffix        XIZP
UMS job           ZWE1XIZP

Broad selector    ZWE*
UMS name matches  YES

A job-name match alone is not the entire rule. Addresses, ports, direction, priority and other filters determine which rule actually applies. A broad port scope combined with ZWE* can inadvertently select UMS.

Architecture recommendation

Scope the sockets deliberately

Prefer rules limited to intended Zowe services and their actual listening or destination ports. Where exceptions are used, validate Policy Agent selection and precedence on your system.

Conceptual policy intent — not PAGENT syntax

Zowe core socket → intended AT-TLS policy
UMS API socket  → native TLS, no Zowe AT-TLS
UMS outbound    → no blanket Zowe wrapping
Backend socket  → its documented TLS policy

An inbound exclusion for ZWE1XIZP does not automatically exclude a socket owned by the App Server or Gateway. Inspect both endpoints and both directions.

03 / Inspect the handshake

Who expects the first TLS record?

Fixed server: UMS API native TLS is enabled. This simplified teaching model illustrates protocol ownership; it does not simulate every AT-TLS mode or error code.

Failure A · Stack decrypts a handshake intended for UMS

If transparent inbound AT-TLS consumes the client’s TLS handshake, UMS’s native TLS listener receives decrypted application bytes instead of the TLS records it expects. The connection can fail during handshake or request processing. Exact messages depend on the active policy and runtime.

Failure B · Both the application and stack try to wrap TLS

Native TLS plus transparent AT-TLS on the same client socket can create nested TLS or a handshake mismatch, depending on the peer policy. Even if a symmetric arrangement appears to work, it is not a supported substitute for IBM’s UMS exclusion. Assign one TLS owner per endpoint for each intended TLS session.

Failure C · Exclusion succeeds, but certificate trust fails

Correct rule selection does not establish trust. The native TLS client still needs the issuing CA chain, a certificate matching the requested host name, permitted TLS versions/ciphers and any required client identity. Do not resolve this by disabling certificate validation.

Identity is a separate layer from encryption

TLS server authentication, mutual TLS, JWTs, SAF authorization and PassTickets solve different problems. A successful handshake does not prove that the right user was authenticated or authorized. Zowe specifically warns about sending a server certificate to southbound services that accept X.509 client authentication, because the server identity may be authenticated instead of the end user.
